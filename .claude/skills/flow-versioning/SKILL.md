# Flow 버전 관리

사용자 지시(2026-11-21): **버전 정보는 당연히 붙인다.** 앱 코드가 바뀐 커밋마다 버전을 올리고 이력을 남긴다. 묻지 않는다.

## 번호 규칙 `큰.중간.작은+빌드`

| 자리 | 올리는 때 | 올리면 |
|---|---|---|
| 큰 | 화면·데이터 구조를 크게 바꿈 (예전 저장 파일과 안 맞을 수 있음) | 중간·작은을 0으로 |
| 중간 | 사용자가 볼 수 있는 새 기능 | 작은을 0으로 |
| 작은 | 버그 수정, 작은 손질, 문구·스타일 | — |
| +빌드 | 버전을 올릴 때마다 항상 +1 (줄이지 않음) | — |

- 문서·skill·tools만 바꾼 커밋은 버전을 올리지 않는다(앱이 같으므로).
- 한 요청 안에서 커밋이 여러 개여도 버전은 한 번만 올린다. 단, 이미 태그를 push한 뒤 같은 요청에서 다시 고쳤으면 태그를 옮기지 말고(force 금지) 다음 작은 번호로 올린다.

## 버전이 적힌 곳 (셋 다 함께 고친다)

1. `pubspec.yaml` → `version: 1.1.1+5`
   - Windows 빌드가 이 값을 `flow.exe` 파일 속성(파일 버전·제품 버전)에 자동으로 넣는다(`windows/runner/Runner.rc`의 FLUTTER_VERSION).
2. `lib/app_version.dart` → `appVersion = '1.1.1'`, `appBuild = 5`
   - 창 제목 `Flow v1.1.1` (`lib/main.dart` WindowOptions.title)
   - 설정 창 왼쪽 아래 `Flow v1.1.1 (빌드 5)` (`lib/widgets/settings_dialog.dart` actions)
3. `CHANGELOG.md` 맨 위에 새 항목:
   ```
   ## 1.1.1 (+5) — 2026-11-21
   - 사용자가 알아볼 말로 바뀐 점 한 줄씩
   ```

`test/app_version_test.dart`가 (1)=(2), CHANGELOG 맨 위=현재 버전인지 검사한다. 하나만 고치면 `flutter test`가 실패한다.

## 절차 (앱 코드 변경 작업 끝에)

1. 변경 종류로 다음 번호를 정한다 (위 표).
2. 세 곳을 고친다 → `flutter analyze lib test` / `flutter test`.
3. 커밋 메시지 첫 줄 끝에 버전을 붙인다: `Add version display (v1.1.1)`.
4. 태그를 달고 브랜치와 함께 push한다:
   ```
   git tag -a v1.1.1 -m "Flow 1.1.1"
   git push origin <작업 브랜치> && git push origin v1.1.1
   ```
5. 사용자에게 "이번 버전: v1.1.1"을 알려준다.
